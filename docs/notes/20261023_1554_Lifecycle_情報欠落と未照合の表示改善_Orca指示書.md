# Orca Coordinator 指示書 — Lifecycleの情報欠落・未照合の表示改善

作成日時: 2026-10-23 15:54 JST  
対象: `igomuni/nihon-no-yosan`  
作業種別: 既存Lifecycle試作の表示改善（実装・テスト・PR作成まで。**マージ・公開操作はしない**）

## 1. Objective / 背景

`https://igomuni.github.io/nihon-no-yosan/#/lifecycle` の「予算の一生の表（試作）」を、概算要求・政府案・補正・決算に情報が揃わない項でも、事実を誤認せず比較・調査できるUIへ改善する。

最優先は「欠けている値や未確定な関係を勝手に埋めない」こと。欠落を無理に隠すのではなく、**どの段階の値を観測できたか、何が確認できていないか、比較できる範囲はどこか**を画面上で分かるようにする。

既存の実装・判断を尊重する。Lifecycleは現時点でFY2023・FY2024の試作で、`kou` と `events`、段階別のグラフ、Wide/Longの2形式、および `checks` を持つ。既存の「空欄≠0」「原本/導出の分離」「原本にない関係を公式と断定しない」を引き継ぐ。

## 2. Source of truth / Pre-flight

1. 作業開始時に `https://github.com/igomuni/nihon-no-yosan` の**最新の `main`、関連する未マージPR、現在のworktreeとHEAD**を確認する。古い会話のSHAやファイル構成を固定しない。
2. 関連の恒久仕様・決定を読む。特に `docs/decisions/0003-budget-lifecycle-model.md`、`docs/guides/budget-lifecycle.md`、`docs/guides/data.md`、`docs/guides/web-publish.md`。当該画面・データ・グラフの現行実装（参考: `apps/web/src/lifecycle/`、`packages/core/src/lifecycle*`、`packages/pipeline/src/build/lifecycle*`）も確認する。
3. 各段階・各値の出典、`seenIn`、`original` / `derived`、突合の信頼度・未収録の区別を**現行のデータからどこまで判断できるか**を最初に棚卸しする。この段階で判別不能な状態を、UI上の確定状態として実装しない。
4. Orca Coordinatorが担当worktree・task branch・Worker構成・依存順を管理する。canonical checkout、取得原本、凍結済みartifactはread-only。変更対象は担当worktree内のみ。

## 3. 実装スコープとUI要件

### A. 段階を固定したステータス表示（優先度P0）

項の詳細の上部に、原則として次の4つの段階を**常に同じ順・位置**で表示する。

`概算要求 → 政府案 → 補正 → 決算`

- 値のある段階: 金額と意味を表示。値0が実際に観測された場合は明確に `0円` と表示する。
- 値のない段階: カードを消さず、`—` と**理由の分かる範囲で**状態を併記する。
- 画面が根拠を持てる場合のみ、`対象資料に該当行なし`、`対応未確定`、`未収録`、`対象外` 等を使い分ける。
- 現行データの `seenIn` 等から存在しない理由を判別できない場合は、**`現行データに値なし（理由未確定）`** などと表示し、公式資料に項が存在しなかったことまで断定しない。
- `0円`、`値なし`、`該当行なし`、`未照合`、`対象外` を同義に扱わない。
- 段階に代表する金額を明示する。例: 概算要求は要求額、政府案は政府案額、補正は改予算額、決算は支出済額。決算の歳出予算額・歳出予算現額・支出済額は**異なる指標**なのでラベルなしに取り替えない。
- 補正レコードがないときに、政府案額を「観測された補正後額」として表示しない。集計・表示上の便宜として政府案額を用いる場合は「補正の記録なし／補正後相当は導出・表示用」等と明示し、既存の値を上書きしない。
- `original` / `derived` が金額に付いている場合は、詳細から必ず確認可能にする。原本の項別の額が目の合計で導出されたケースも維持する。

### B. グラフでの欠落・関係の不確実性（優先度P0）

- **観測した値の点・棒**と、**段階間の対応関係を表す線・矢印**を区別する。
- 対応関係が確定しない区間を、単なる時系列順や金額の近さで実線接続しない。未観測の値を内挿、0補完、前後値での補完もしない。
- 対応候補が現行データで明示的に保持されている場合に限り、破線等で**候補であることを明記**して示せる。候補の根拠が無い場合は破線すら描かない。
- 現在の棒グラフ等を活用してよい。新しい線グラフの導入自体は必須ではない。見た目より意味の正確性を優先する。
- 不明な差額の原因を、組み替え・査定などと断定しない。現行の「原因未確認」を維持する。
- 一般会計・特別会計をまたぐ合計の二重計上注意、異なる予算段階をサンキーの金流にしない方針を維持する。

### C. 集計範囲の明示と比較モード（優先度P1）

項を選択する前の概要、または一覧上部に、次の2つの視点を分けて表示する。

1. **観測額（全体）:** 各段階で値を確認できた項の合計。段階ごとに母集団が異なり得るため、各段階の項数・対象年度・会計を併記する。段階間の差を単純に「査定差」等と断定しない。
2. **比較可能な項:** 比較対象となる2段階の値・同一性の根拠が揃う集合に限定した合計・比較。**どの段階間の比較か、両側に値がある項数、除外件数・理由**を明示する。根拠不足なら「比較不能」と表示し、無理に差額を計算しない。

すべての段階が揃う項に限定した比較を加える場合もよいが、二段階比較と混同せずラベルで区別する。FY2023/FY2024・一般/特別会計・フィルタ変更に連動させ、対象集合が変わる場合は明記する。現状の集計ロジックで政府案のある項だけを数えるなどの条件がある場合、黙って「全項」と呼ばない。

### D. 欠落パターンでの絞り込み（優先度P1）

既存の項一覧に、少なくとも次の表示上のフィルタを検討・実装する。

- すべて / 全段階に値あり / 一部段階に値なし
- 政府案の値なし / 決算段階の値のみ（現行の**登録・対応済みデータ内**での定義を表示）
- `対応未確定` の専用フィルタは、その状態を判定する根拠データが現在存在する場合にのみ実装する。無ければ追加せず未対応として報告する。

絞り込み条件と各件数を既存の検索・年度・会計フィルタに整合させる。状態を判定できない理由のある項は、意図せず「欠落がない項」へ混入させない。

### E. 詳細データへの導線（優先度P1）

詳細表示は、**上部: 段階別の状態と金額 → 中央: グラフや比較 → 下部: 検証可能なデータ**の順に整理する。

Wide/Longの表、出典、単位、原本値/正規化値、検算情報は削除しない。一般利用者向けの主画面より後方（折り畳み、タブ等）に置くことは可。原本と出典へ戻るための情報は常に辿れる状態を維持する。

## 4. 意味の境界・変更禁止事項

- `seenIn` や出力CSVに行がないという事実から、**公式原本にも該当項が無かった**と断定しない。対象資料の取得状況・抽出状況・突合状況は別物。
- `not found` / `unresolved` / `ambiguous` / `not applicable` を、根拠なしに作らない。「UIに必要だから」という理由で意味フィールドを推測生成しない。
- 空欄、null、欠損を0へ変換しない。金額一致から項の同一性を確定しない。別所管・別年度・別会計を混同しない。
- 出典と変換と表示を区別する。既存の生データ・基準データの金額・照合結果を、UIの都合で変更しない。
- 当Taskは**UIおよび表示に必要な純粋なderived view-modelとテスト**に限定する。Lifecycleの意味仕様そのものの変更、データ抽出器・基準データ・public Releaseの再生成、PDF取得、新しい自動マッチングアルゴリズムの実装はしない。
- `links` テーブルがまだ存在しないなら、本Taskで推測実装しない。対応状態を見分けるために新たなデータ契約が必須になった場合は**STOP / escalation**し、根拠・候補・判断事項を報告する。根拠のある表示のみ先行可能ならその範囲を独立して完了する。
- PDL1.0の適用等の利用条件や公開範囲を、本Taskの裁量で変更しない。

## 5. 実装進行・Validation

Coordinatorは段階的に進める。まず現行データで**確実に区別できる状態の対応表**（画面ラベル、判定根拠、判定できないケース）を短いドキュメントにし、その根拠がある表示のみ実装する。通常の開発Taskとして扱い、GT凍結・preregistration等の研究手順は要求しない。

最低限のテストケース:

1. 4段階に値がある項（全段階表示と正しい値ラベル）。
2. 決算段階にしか値がない項（他段階は0ではなく値なし。無断の線接続なし）。
3. **原文で明示された0**と、**レコードの不存在**を画面上・テスト上で区別。
4. 政府案はあるが補正レコードがない項（補正後の表示用導出と原本値の区別）。
5. 対応未確定または抽出不足により理由不明のケース（根拠のない「該当行なし」への昇格禁止）。
6. 段階ごとの観測額と、比較可能な共通項集合での集計の母数・金額。会計・年度・検索の切り替えによる追従。
7. `original` と `derived`、決算内の歳出予算額／歳出予算現額／支出済額が混同されない。
8. 既存の検算結果・リンク・一覧・Wide/Long表示が失われていない。

`npm ci`、`npm run check`、`npm run build`（現行コマンドに変更があればそれに従う）を実施し、可能なら既存の基準データを使ってFY2023・FY2024のブラウザ実機確認（一般/特別、欠落と0の例）を行う。ローカルデータや検証環境が無い場合、実施した範囲と未確認を区別して報告する。既存の検算値と対照し、画面の集計変更が意図した母数差なのか検証する。

## 6. Deliverables / Git / PR

- 画面実装、表示判定の純粋関数・テスト（必要な分のみ）。
- 状態ラベルの意味と判定可能性、集計母集団、未実装の関係を説明する恒久ドキュメントの更新（適切な `docs/guides/`）。
- `docs/tasks/YYYYMMDD_HHMM_{タイトル}.md` に実施内容と検証結果を記録（日本時間。タイトル直後に状態・結論を1〜2行）。`docs/tasks/INDEX.md` は通常Taskのついでに更新しない。
- 独立したtask branch、担当worktreeでcommitし、pushし、レビュー可能なPRを作る。既存の未マージPR等に依存する場合は依存関係を記載する。
- **merge、approve、Ready化、Releasesアセット更新、Pages公開・デプロイ操作、原本・凍結データの変更はしない。** 想定外のconflict、branch/worktree不一致、テスト不合格、意味仕様の変更必要性を発見したらSTOP / escalation。

## 7. Coordinator 最終報告フォーマット

以下を統合報告としてユーザーへ返す。Worker報告の単なる連結は不可。

- **Status:** COMPLETE / PARTIAL / STOP / ESCALATION
- **現在地点:** base/main SHA、worktree、task branch、HEAD、PR URL
- **観測:** 現行データから確定できた欠落・照合状態と、判別不能な状態
- **実装:** 画面で変えた箇所、対応するスクリーンショットまたは操作確認、主要なファイル
- **意味の整合:** 0/値なし/未照合/未収録、原本/導出、集計の母集団をどう分けたか
- **Validation:** テスト、build、実データ確認、既存の検算との一致・不一致
- **未解決:** 新しいデータ契約・調査・ユーザー判断を要する事項（根拠を添える）
- **Git:** commit SHA、push先、PR、作業ツリーclean確認
- **提案:** 次のGO / STOP判断。未確認事項を解決済みとは記載しない
